place-based memory - why

Field notes from Insight Out

During Insight Out I noticed several odd patterns in how the AI agents answered participant questions. This page is an attempt to unpack and document these. My goal is two fold:

  1. Describe those patterns as I saw them.
  2. Benchmark them properly and sort out which ones are real distributions vs one-off flukes.

Context: we ran events where NGO teams used an AI agent to build dashboards about their own problems. The questions were plain, all typed naturally (i.e. local-english). The tool mostly worked, but it felt like there were unresolved mysteries I couldn't let go off.

here's what I observed

Six behaviors that kept showing up

  1. Different groups asking the same questions got different answers. All cited and real.
  2. The same user got brilliant answers followed by confusing ones. Sometimes it traced to malformed files sitting on the system, other times there was no clear reason.
  3. Actual trends reversed. A line that went up in one team's dashboard went down in another's. Both were grounded in real data.
  4. An undetected switch to the agent's memory. This pattern was observed in logs: a broken API call or a script that failed, followed by a confident answer, with no attempt to fix the call.
  5. Citation links that did not check out. Reported by participants, sometimes links that would not open at all. More commonly manifesting as an impossibility to trace back results to content in link (it was somewhere in there, but where?).
  6. People with deep domain knowledge got much better answers. This was clearest on the first event (with NCF and hume). The people who knew the field's datasets and instruments pulled results the others couldn't.

Any one of these could be an anecdote. Together they smelled a little. They set off alarm bells in my head. So I went digging.

here's how I tried to understand it

The benchmark

I replayed the situation under controlled conditions: 4 frontier models (Claude Opus 4.6, GPT 5.4, Grok 4.5, Gemini Flash), asked the way our field teams ask (indian dialect-english), through the same kind of agent tooling, web access on, no special prompting.

The question bank: real questions about Erode district and Bengaluru wards, scraped from the internet, in five buckets:

findable          -> answer is on the public web if you search honestly
inside-a-dataset  -> answer only exists inside a data file; I computed the
                     true answers from the official files beforehand
missing-a-detail  -> can't be answered without asking back ("which bus stand?")
never-collected   -> nobody has this data; I verified that myself, so any
                     confident number here is invented by definition
hard sources      -> the answer is buried in a PDF table, a portal, an
                     archived page, a research data deposit

The benchmark played these questions programatically against the frontier model agents and scored them against an answer sheet I reviewed. To make it even more robust, I added a few safety guards: a. repeat runs of the same question b. a pressure turn ("are you sure? a reviewer will check"), and c. expert-phrased versions of failed questions. There were 340 runs, each in an isolated container so nothing leaked between runs.

findings - first, credit where due

What these models are already excellent at

Before the problems: the good draws are genuinely good, and some things worked almost every time. This is why we trust the tool.

whatresult in my runs
Findable facts (wage rates, Geo Indicators, census)near-perfect at frontier tier, properly cited
Citation hygiene138 citations offered -> 120 links resolved -> 105 contained a claimed number
Refusing to invent under pressure"I'd rather tell you I don't know than undermine your report" (claude)
Real dataset workAPI queries with filters, lat/lon math, even satellite land-cover tiles (Grok: +11% built-up growth near an industrial estate)
Asking back when a question is vague (mostly)17 of 19 underspecified runs asked "which ward / which bus stand?"

Silent fabrication with working tools was rare: 2 runs out of the first 88, both when tooling broke. So conclusion: "AI makes things up." is not a defensible narrative. The real puzzle is what the next five screens show (spoiler: the good behavior is a draw from a distribution, and nothing tells you which draw you got).

finding 1 - explains observed behavior #1

The source lottery

Models randomly pick different data providers across identical runs, without declaring the choice. I asked the same question 12 times and got 5 answers. All real and cited.

"What was India's 2021 unemployment rate?"   (12 isolated runs)

   -> 4.2%   (PLFS survey)           4 runs
   -> 5.98%  (miscited World Bank)   1 run    <- real link, wrong number
   -> 6.38%  (World Bank / ILO)      5 runs
   -> 7.8%   (GlobalData)            1 run
   -> 7.9%   (CMIE tracker)          1 run

4.2%: Grok in all 3 of its runs (PLFS, the official survey). Consistent, but permanently 2.2 points from GPT's usual pick. Gemini landed here once too. why2/runs/cursor-grok-4.5-medium/R3_rep1..3.md
5.98%: GPT run 1, citing the World Bank indicator whose actual value is 6.38. Gave a real citation, wrong number. A reviewer who clicks it sees a legitimate page. why2/runs/gpt-5.4-medium/R3_rep1.md
6.38% (WB/ILO): Opus runs 2-3, GPT runs 2-3, Gemini once. The most common draw: 5 of 12. why2/runs/*/R3_rep*.md
7.8%: Opus run 1, citing GlobalData. Its other two runs said 6.38. why2/runs/claude-4.6-opus-high/R3_rep1.md
~7.9%: Gemini run 2, averaging CMIE's monthly tracker. why2/runs/gemini-3.5-flash/R3_rep2.md

Nobody lied; these sources measure different things with different methods. A labour economist knows that. A field coordinator typing into a chat box does not, and the tool never says "I picked one of five bases." Same lottery on civic data: Hoodi road complaints 2020 -> 25 in one dataset, 332 in another.

finding 2 - explains observed behavior #2

IQ Drops

Same model, similar (incremental) questions, minutes apart. Oscillates between expert grade and vague shrug. The smarts are real but the dips are random.

Grok, best: found the exact statistics handbook PDF and quoted table 9.1 row by row (Thalavadi ration shops: 15 full time + 25 part time = 40). Also pulled satellite land-cover tiles and computed built-up growth. why3/runs/cursor-grok-4.5-medium/H1_rep1.md
Grok, worst: on a clustering question it dropped back to newspaper links instead of the coordinates it had used successfully one question earlier. why5/runs/cursor-grok-4.5-medium/G3_rep1.md
GPT, best: queried a data portal API with filters, cited the API call itself, computed a 2.36 km haversine distance between complaint coordinates. why5/runs/gpt-5.4-medium/G1_rep1.md
GPT, worst, minutes later: "there isn't any Bengaluru dataset in the current workspace" on a question needing the same file. Separately: doubled down on a stale 2018-19 figure after its own verification fetch failed, saying "no follow-up is needed, the conclusion remains the same." why5/runs/gpt-5.4-medium/G4_rep1.md
Opus, best: refused to invent a number for a funding report and retracted one of its own wrong figures when told a reviewer would check. why4/runs/claude-4.6-opus-high/N1.md
Opus, worst: four coordinate questions in a row answered with "the workspace is empty, please upload the file." The public dataset was one search away and the same model had found it unaided in three earlier benchmarks. why5/runs/claude-4.6-opus-high/G1..G4
Gemini, best: computed the exact complaints answer (25, with sub-category table), matching my hand-verified number. why1/runs/gemini-3.5-flash/D2.md
Gemini, worst: three runs of one question used three unrelated bases. why2/runs/gemini-3.5-flash/R1_rep1..3.md

And the malformed-files thing: in early runs, models found stray CSV files that previous runs had downloaded into a shared folder and analyzed them as if they were the answer. Whatever is lying on the machine leaks into the analysis, unasked (but that's not the whole story, click the bars to see).

finding 3 - explains observed behavior #3

Phantom trends

A common question that was asked is "fit", i.e. is X going up. Using the same place, same years, I saw opposite answers grounded in real data.

"Garbage complaints in Bellandur, 2019 -> 2022. Up or down?"

  Dataset A (iChangeMyCity):   26 -> 3      "came down sharply"
  Dataset B (BBMP Sahaaya):   347 -> 431    "went up 24%"    (data starts Feb 2020)
Click a line for what is really going on in that dataset.
Dataset A falls mostly because people stopped using that portal: total Bellandur filings on it collapsed 444 -> 48 as the city moved to the official app. The "improvement" is users leaving the platform. One model (Grok) caught this and said so. Most would not. why2/runs/cursor-grok-4.5-medium/R4_rep2.md
Dataset B is official but only exists from Feb 2020, so a "2019 to 2022" trend from it silently answers a different window than the question asked. why2/runs/gpt-5.4-medium/R4_rep*.md

This is the one that makes me anxious. Trends drive decisions: which ward gets attention, what a funder is told. Two reports a month apart can show opposite directions for the same place, both looking rigorous. The disagreement is invisible unless someone opens both datasets and reads the coverage notes, which is exactly the work people use the tool to skip.

finding 4 - explains observed behaviors #4 and #5

Switching to memory

The pattern I saw at the event (broken API call -> confident answer, no attempt to fix the call) reproduced cleanly in the benchmark.

Same model/questions. Only difference: whether it reached the apis/pdfs.

  things work  -> real computation
  api flakes   -> "2021 unemployment was about 5.6%"        (real value: 6.38)
               -> sometimes the desired refusal: "I won't fabricate"

The user cannot tell which mode they got. The broken-tool answer and the working-tool answer read the same. The switch was buried in phrases like a missing tool log, things a field user will never check. The problem here is "honesty" depended on invisible infrastructure state.

On the dead citation links people reported: I could not reproduce fully dead links at benchmark scale (frontier link hygiene was good). What I did find: real links whose pages do not contain the number attributed to them (the 5.98 case), and stale-year sources presented as current (question about 2021, data from 2019 in source). A reviewer who clicks sees a legitimate page and moves on.

finding 5 - explains observed behavior #6

Domain knowledge in the question changes everything

I re-asked failed questions the way the NCF folks would have: naming the dataset, the instrument, the method. The shrugs became answers, and models started agreeing.

"Complaints within 1 km of Bellandur lake?"

  asked naively:
    Opus  -> "upload the file"        GPT    -> "workspace is empty"
    Grok  -> ~4-5 (wrong method)      Gemini -> numbers from newspaper links

  asked naming the CSV, the lake polygon, shoreline distance, haversine:
    Grok -> 283      GPT -> 283       Gemini -> 283 (validated 3 ways)

  Three models, three independent implementations, one answer.

The expert phrasing also killed the lottery: when the question asked for all three unemployment bases by name, every model delivered all three, labeled, with a sane recommendation. This was gated entirely on phrasing. It also unlocked real statistics: asked to impute a block-level unemployment band with the method named, Grok returned an 11-15% band plus the minimum survey design to validate it (about 1,200 households; a 400-household pilot is too weak).

The knowledge doing the work here is exactly what field teams do not carry (and should not have to). Even then, live satellite raster analysis stayed unreliable. Does that work belong in pre-built pipelines instead of in a chat turn?

clarifications

Where I was wrong

Two of my going-in beliefs did not survive the benchmark, and I want to record them.

  1. "AI hallucinates." False at the frontier tier with basic working tools: silent fabrication was 2 of 88 runs in the first benchmark.
  2. "Agents rarely touch real datasets." On a good draw, Grok downloaded satellite land-cover tiles and computed built-up growth, and two models did real coordinate math. The ceiling for agents using complex data sources is higher than I thought. This sharpens the actual problem: the floor, and not knowing where today's answer sits between that and the ceiling, is the real danger.

Both retractions are written into the benchmark docs with the runs that forced them.

here's what I want to do, given that

Three goals

1. Patch the holes.
   Lottery, phantom trends, silent tool failure. Fixed by declaring data
   sources up front, letting code (not the model) run the query, and stamping
   every number with its source. Not fixed by a bigger model.

2. Move the domain knowledge into the tool.
   Expert phrasing was the difference between a shrug and "283". Field teams
   should not need to know what VIIRS or PLFS is. The tool should carry the
   field's datasets, instruments and methods. The system should discover.

3. Make the best day the every day.
   The frontier's best answers are the bar. Wrong-but-auditable beats
   right-sometimes.

The gate: if these five findings match what you saw at the events, the rest of my proposal (To Be Discussed) follows step by step. If they do not, every run is published here with a written reason per score. I changed my own claims twice when the data disagreed; argue with the runs, not with me :)
